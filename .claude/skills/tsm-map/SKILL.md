# Carte du code TSM

Deux repos qui travaillent ensemble. **Ne pas ré-explorer ce qui est décrit ici — les chemins sont vérifiés.**

Pour le détail fichier par fichier de tsm-backend (rôle + options CLI de chaque script), voir **`REPO_CONTEXT.md`** à la racine du repo — lire la section concernée au lieu de fouiller `collectors/`/`scripts/`.

## Flux de données global

```
tsm-backend (Python, local, Task Scheduler)  →  R2 (bucket prod: taylor-data)  →  tsm-frontend API (FastAPI/Vercel)  →  React
```

- Bucket R2 **prod = `taylor-data`** (R2_APP_BUCKET non défini sur Vercel). Le `.env` **local** de tsm-frontend pointe sur `taylor-app` → les settings/uploads locaux ≠ prod.
- `tsm-backend/website/` = site statique **LEGACY, interdit** sauf demande explicite (règle CLAUDE.md).
- Préfixes/clés R2 : source de vérité = `tsm-backend/scripts/r2_keys.py`, miroir tenu à la main côté frontend = `tsm-frontend/api/data/r2_keys.py`. Quelles données R2 sont pérennes vs cache jetable → skill `scripts-maintenance` § "R2 : données pérennes vs cache".

## tsm-backend (`c:\Users\sfara\Documents\GitHub\tsm-backend`)

- CLI : `python -m tsm daily` et `python -m tsm collect charts` (code dans `tsm/cli.py`). Launchers racine : `run_daily.bat`, `run_all_charts.bat`.
- `collectors/` : `spotify/` (streams + charts), `apple_music/`, `billboard/`, `youtube/`, `comp/`, `website/`.
- Pipeline streams : `collectors/spotify/streams/update_streams.py` ; outils dans `collectors/spotify/streams/tools/scripts/` (`history_store.py`, `spotify_api.py`, `reconcile_gap_catchup.py`, `generate_albums_image.py`, `post_albums_twitter.py` hors week-end).
- Catalogue maître : `db/discography/artist.json` ; cache covers : `db/discography/track_cover_cache.json`.
- **Clé de jointure interne du catalogue** : `db/discography/tsm_id_registry.json` (source de vérité, `tsm_song_id`/`tsm_album_id` gelés) + `catalog_index.{json,csv}` (vue à plat). Générés par `scripts/assign_tsm_ids.py`, portés dans l'export web (`data/songs.json`/`albums.json`). Utiliser `tsm_song_id` plutôt qu'un match par titre pour relier une chanson entre collectors. Détail → skill `scripts-maintenance`.
- Ops détaillées → skill `pipeline-ops`.

## tsm-frontend (`c:\Users\sfara\Documents\GitHub\tsm-frontend`)

- `frontend/` = React 19 + Vite, build vers `../public`. `api/` = FastAPI (`api/index.py`, routes dans `api/routes/` : `site_settings.py`, `leaderboard.py`, `daily.py`, `news.py`, `journalist.py` (fact-checks + tips anonymes + votes helpful + watchlist « comptes à signaler »/Twitter notes (community notes d'autrui à aller noter SUR Twitter, badge consigne helpful/not_helpful) + traductions DeepL des notes de `/journalist-department`), `image_proxy.py`, `admin_upload.py` (Media Library, tokens admin OU journalist ; les 302 `/api/landing-media/` ont un cache court + cache-buster `landingMediaSrc()` — piège cache 7 j corrigé juillet 2026), `version.py` (`/api/version`, dates de dernier snapshot par collector — streams/charts/tayboard/apple music/youtube, poll léger cache CDN 5-10min), `home_highlights.py` (`/api/home-highlights`, précalcule côté serveur le pool de highlights de la Charts Gallery — réutilise `get_version`/`get_charts`/`get_apple_music` + les loaders directement en appel Python plutôt que HTTP interne — évite au client de fan-out sur 6+ endpoints), `data/precompute_cache.py` (cache R2 générique `read_fresh_cache`/`write_cache`, clé `cache/*.json` + horodatage `_cache_generated_at` — utilisé par `version.py` et `home_highlights.py` depuis 2026-07-28 : `get_charts`/`get_apple_music` refont un matching chanson complet sur tout l'historique CSV à chaque appel, donc ces deux routes lisent d'abord ce cache (5 min) avant de recalculer ; `signal_updated_at` reste lu en direct hors cache pour ne pas retarder la bannière live), etc.).
- **Qui écrit vraiment ce cache** : depuis 2026-07-28, c'est `tsm-backend/scripts/generate_home_highlights.py` qui régénère `cache/home_highlights.json`/`cache/version.json` (best-effort, en fin de `update_streams.py`/`run_all_charts.py`/`run_apple_music.py`/`swift_top_100.py`/`swift_top_albums.py`) — le calcul côté frontend (`read_fresh_cache` miss → recompute → `write_cache`) n'est qu'un filet de sécurité si le backend n'a pas encore tourné ou a échoué. Le script backend n'a PAS porté le matching flou de `api/routes/charts.py` : pour le highlight `chart_1`/mouvements NEW/RE, il lit directement `db/charts_history_global.csv` (track_id/movement déjà résolus par le collector à la collecte) plutôt que de dupliquer `_pick_best_song_match`.
- **Types de highlights (2026-08-14)** : `most_streamed`, `biggest_gainer`, `total_daily`, `milestone`, `surpass`, `best_day_since` + `oldest_record` (record `kind="since"` au `days_since` max, séparé du pick principal pour ne pas être écrasé par un `best_ever` du jour), `top_album`/`top_era`/`tayboard_1` (masqués si le chart TayBoard a plus de 2 jours vs `latest_date`), `apple_music_1`, `chart_1`/`chart_new`/`chart_re`, `regional_climb` (plus gros bond de rang jour/jour, seuil 20 places, `global`/`fr`/`us`/`uk` confondus), `best_rank_since` (meilleur rang Spotify Charts ou Apple Music depuis ≥14j, `source="spotify_charts"|"apple_music"` — voir ci-dessous). Le rendu/label/lien par type vit côté frontend dans `components/ChartsHighlights.jsx` (`LABEL_KEYS`/`LINK_BY_TYPE`/`localizeHighlight`) — toujours garder les deux fichiers en phase quand un type change.
- **`best_rank_since` est le seul highlight qui persiste entre les runs** : tous les autres types sont recalculés from scratch à chaque exécution de `generate_home_highlights.py` et disparaissent dès qu'ils ne sont plus vrais le jour même. `best_rank_since` doit rester affiché ≥14 jours après son déclenchement (décision produit 2026-08-14) — `main()` lit donc le cache existant avant d'écraser (`get_cache_json`), garde les items `best_rank_since` encore dans leur fenêtre via `merge_persisted_best_rank_since`, et les rajoute à la liste fraîchement calculée. Calcul : `compute_spotify_rank_since_highlight`/`compute_apple_music_rank_since_highlight` dans `generate_home_highlights.py`, primitif partagé `collectors/spotify/core/rank_since.py`. Détail → skills `spotify-charts`/`collector-apple-music`/`data-rules`.
- **Même logique côté page détail chanson** : `SongDetail.jsx` (Spotify Charts) et `AppleMusicSongDetail.jsx` affichent un badge `RecordStar` (`components/RecordStar.jsx`) quand LA chanson elle-même a un `best_rank_since` actif dans les 14 derniers jours — calculé **côté client** à partir de l'historique déjà chargé (`utils/rankSinceBadge.js`, port JS du même algorithme), pas depuis le cache highlights (qui ne contient qu'un seul gagnant par source/run, pas un par chanson).
- **`api/routes/charts.py::/api/charts/discography` (History view de Spotify Charts, 2026-08-26)** : sert `songs` (agrégat par chanson : `last_*`, `peak_rank`, `peak_streams`, `total_days`, `longest_streak`/`longest_streak_active`) + `previous_songs` (même agrégat mais en excluant la dernière date chartée de la région/du pays — baseline "hier" stable). `region` global/fr/us/uk lit d'abord le cache précalculé côté backend (`tsm-backend/scripts/build_spotify_chart_discography.py` → `{region}.json` + `{region}_previous.json`, voir `REPO_CONTEXT.md` § 8) ; `region=overall` et les pays worldwide hors global/fr/us/uk recalculent toujours en live (`_build_discography_by_key`/`_build_worldwide_country_discography_by_key`, jamais le cache backend) — toute logique de streak/previous ajoutée doit donc vivre dans les DEUX chemins, pas juste dans le script backend. Le frontend (`TsTracker.jsx`) ne garde plus de "baseline" capturée au clic sur un tri (`historyRankBaseline`, source du bug où changer de colonne de tri faussait le rank change) : `sortDiscoSongs()` (fonction pure, module-level) trie `previous_songs` avec le MÊME comparateur que `songs` pour la colonne active, et le mouvement de rang est toujours `position hier − position aujourd'hui` sous ce même critère.
- **History view — 2 sous-modes (`TsTracker.jsx`, param `?mode=country|song`, 2026-08-31)** : boutons secondaires dans la `.chart-toolbar` visibles seulement si `view=history`. `mode=country` (défaut, param omis) = le comportement ci-dessus (picker de région → agrégat par chanson). `mode=song` = mode "Per Song", rendu en **sections empilées** (`SongCountrySection`, 1 par chanson : header cover/titre + tableau transposé — 1 ligne par pays où la chanson a charté : Country / Last Charted / Last # / Last Streams / Peak Rank / Peak Streams / Days / Longest Streak) :
  - **par défaut (pas de `?song=`)** : toutes les chansons présentes sur le **dernier snapshot Global Spotify Charts**, triées par rang Global — **chaque section ne montre QUE la ligne Global** (pas de tri, `sortable={false}` ; le détail par pays vient quand on pick la chanson). Sert `GET /api/charts/discography/songs` (`getChartsGlobalSongsCountries`) → `{latest_date, songs:[{track_id, song_name, image_url, latest_date, countries:[<ligne global uniquement>]}]}`. **Précalcul only** (pas de fallback live — dépend de `song_countries.json`, présent dès le 1er run de charts post-deploy).

Sert `GET /api/charts/discography/song/{track_id}` (`getChartsSongCountries`) → `{track_id, song_name, latest_date, countries:[...]}` ; lit `song_countries.json` d'abord, **fallback live léger = base regions global/fr/us/uk uniquement** (`_build_song_countries_live`).
  `song_countries.json` = pivot par track_id écrit par `build_spotify_chart_discography.py` (voir `REPO_CONTEXT.md` §8). Tri des lignes pays via `sortSongCountryRows()` (fonction pure, module-level) + state `songSortBy/songSortDir` (défaut `peak_rank` asc) séparé du `historySortBy` ; header sticky seulement en vue mono-chanson (`.is-solo`). `mode`/`song` sont strippés de l'URL quand `view!=history` ou `mode!=song`.

Depuis 2026-08-28, le handler merge `charts_discography/peaks_by_track.json` (écrit par `build_spotify_chart_discography.py`, voir `REPO_CONTEXT.md` §8) par clé `"<track_id>|<country>"` : ajoute `peak_streams` + `days_at_peak` (absents du snapshot), complète `peak_rank`/`total_days`/`streak` (← `current_streak`) seulement si manquants. Stockés dans R2 `site_settings.json`, servis/modifiés par `api/routes/site_settings.py` : PATCH **par section** (`PATCHABLE_SECTIONS`), normalisation `_normalize_settings`, auth admin `X-News-Token` (`require_admin_token`), backups auto.

## Fuseaux horaires (frontend)
- `utils/format.js` : `detectTimeZone()` (via `Intl`) → `setFormattingContext` dans `App.jsx` → toutes les fonctions de `format.js` rendent dans le fuseau du visiteur.
- **Dates seules** (`YYYY-MM-DD` : snapshot, chart date, sortie) → `formatIsoDate()` (ancre `T12:00:00Z`, aucun décalage). **Ne jamais** les passer dans un formateur d'heure.
- **Instants** (avec une heure) → `formatDateTime()` (ISO tz-aware, ex. YouTube `snapshot_at` en UTC) ou, pour les timestamps de collecteurs qui sont en heure murale de Paris (Apple Music `scraped_at`), `parseCollectorTimestamp` / `formatCollectorDateTime` / `formatCollectorClock` : elles traitent une valeur sans offset comme `Europe/Paris` (constante `COLLECTOR_TIME_ZONE`) et une valeur avec offset directement. `formatCollectorClock`/`DateTime` ajoutent l'abréviation du fuseau (`GMT+2`).
- Backend : tout timestamp affiché doit être **tz-aware** — `datetime.now(timezone.utc).isoformat()` côté API, offset Europe/Paris pour `scraped_at` Apple Music (2026-08-30). Jamais `datetime.utcnow()` ni d'heure murale nue pour de l'affichage.

## Pièges connus
- La commande de rebuild graphify du CLAUDE.md **échoue** (module non installé) — ne pas la lancer.
- PowerShell 5.1 : stderr des exe natifs (vite, git) affiché en `NativeCommandError` = bruit, vérifier le vrai résultat (« ✓ built »).
- **CSP `img-src` dans `tsm-frontend/vercel.ts`** : header only (pas de meta, pas de code client), donc invisible en dev local — un nouveau host d'images externe (ex. `i.ytimg.com` pour les miniatures YouTube ajouté 2026-08-29 ; `flagcdn.com` pour les drapeaux `RegionFlag` ajouté 2026-08-30) doit être ajouté à `img-src` sinon le navigateur bloque silencieusement l'image (→ `onError` → fallback logo).
